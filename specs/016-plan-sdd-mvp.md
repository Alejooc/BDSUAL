# Spec 016 — Plan de entregas SDD del MVP

Estado: plan vigente; MVP en ejecución
Versión: 0.4
Última actualización: 2026-09-30
Depende de: [000 — Visión](000-vision-y-alcance.md), [009 — Arquitectura](009-arquitectura.md), [015 — Conflictos y aplicación](015-conflictos-y-aplicacion.md)

## Objetivo

Convertir los specs 000–015 en entregas pequeñas y comprobables de DBSUAL para Windows, macOS y Linux, con Windows como primera plataforma de validación. Cada entrega debe producir una capacidad utilizable y evidencia en cada sistema operativo que se vaya a declarar compatible; el mapa y las puertas están en el spec 019.

## Regla de trabajo SDD

Para cada capacidad:

1. Elegir los criterios de aceptación de su spec y registrar las decisiones pendientes que bloquean la implementación.
2. Definir contratos entre interfaz y core, estados de error y pruebas de integración que demuestren el comportamiento observable.
3. Implementar una porción vertical: interfaz, comando Tauri, core, adaptador y persistencia necesarios para ese recorrido.
4. Ejecutar pruebas pertinentes y revisar recorridos nativos en los sistemas objetivo afectados. La evidencia Windows no cierra criterios de macOS/Linux, ni viceversa.
5. Actualizar el spec si la implementación demuestra una limitación real. El cambio de alcance queda visible antes de dar por terminada la entrega.

Un criterio se marca **cumplido** solo con evidencia de una prueba o una revisión manual reproducible. «Compila» no equivale a que el flujo de recuperación funcione.

## Pruebas y evidencia por capa

- **Rust:** contratos, transiciones del historial, clasificación de cambios, validación de destinos, errores de cifrado y reconciliación de trabajos interrumpidos.
- **Integración con bases reales:** operaciones y permisos por motor y versión, conflictos desde otra conexión, respaldos, restauración y objetos especiales. Se usan bases desechables creadas para prueba.
- **Vitest:** prueba el guardado diferido de preferencias, el restablecimiento del panel y el guardado de metadatos de pestañas en `src/store.test.ts`. Ampliar la cobertura a vista previa, diferencias, progreso y bloqueo de acciones sin precondiciones.
- **Playwright en Windows:** recorridos completos de conexión, exploración, lectura, revisión y aplicación, incluida la salida y reapertura de la app cuando un trabajo quedó pendiente.
- **GitHub Actions:** Windows compila, da formato y ejecuta pruebas; jobs nativos de macOS/Linux añadidos para build del frontend y `cargo check`, pendientes de ejecutarse. La matriz aún no produce paquetes ni prueba servicios nativos; se amplía según el spec 019 antes de declarar el MVP multiplataforma. Una prueba que requiere servicios o certificados se identifica explícitamente; no se omite sin dejar constancia.

Cada entrega conserva una ficha breve con spec y criterio, versión del motor, comando o recorrido ejecutado, resultado y limitaciones observadas. Las pruebas de respaldo incluyen **restaurar** y consultar datos, no solo crear un archivo.

## Puertas que bloquean modificaciones

Antes de permitir **Aplicar a la base** en un motor deben funcionar el historial local, la identificación del destino, el estado de trabajos, la clave de cifrado, el proveedor de recuperación exigido y la verificación de conflictos. Si una puerta falla, se mantienen exploración, consultas de lectura y exportaciones que no requieran esa capacidad; la acción modificadora se muestra deshabilitada con una causa comprensible.

La edición de una fila identificable puede usar compensación cifrada según el spec 010. Eliminaciones, importaciones destructivas y SQL de efecto incierto esperan un respaldo completo probado para ese motor. El proveedor SQLite espera además la prueba técnica del spec 013.

## Decisiones antes de iniciar cada entrega

- **Entrega 0:** versiones exactas de herramientas, estructura de paquetes, ubicación de datos locales y migraciones del SQLite interno.
- **Entrega 1:** matriz TLS/SSH de MySQL y pruebas con certificados y agente SSH en Windows.
- **Entrega 3:** biblioteca y formato de cifrado del spec 014; proveedor MySQL del spec 011; pruebas de recuperación de clave tras reinstalación simulada.
- **Entrega 4:** instrucciones SQL e importaciones admitidas, tamaño de lotes y margen de espacio para respaldos.
- **Entregas 5–7:** versiones compatibles, distribución de herramientas nativas y pruebas de restauración de cada proveedor.

Las decisiones restantes se resuelven en el spec de la capacidad antes de escribir su implementación; no se consideran aprobadas por aparecer en esta tabla. La creación de una base vacía no requiere respaldo previo porque no reemplaza estado existente; su aplicación es una excepción acotada y no abre el resto de SQL modificador.

## Criterios de aceptación de este plan

1. Cada entrega tiene un recorrido visible, specs de referencia y una puerta de salida verificable.
2. Una entrega que incluye modificación identifica qué proveedor de recuperación la habilita y qué ocurre si falla.
3. El primer corte funcional usa MySQL y recorre interfaz, core, historial y base real de extremo a extremo.
4. El MVP solo se declara terminado al cubrir los cuatro motores, los criterios obligatorios de los specs 000–015 y la puerta de soporte de Windows, macOS y Linux del spec 019, con excepciones de alcance registradas y acordadas.
